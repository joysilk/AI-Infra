# 07. 실무 역량 (3~5년차에 필요한 것)

> 신입~2년차가 "도구를 쓰는 사람"이라면, 3~5년차는 "시스템과 사람을 안정적으로 움직이는 사람"입니다.

## 1. 장애 대응 절차

### 1-1. 단계 (Incident Response)
1. **탐지**: 알림/사용자 제보. MTTD(탐지 시간) 단축이 목표.
2. **인지·초기 판단(Triage)**: 영향 범위(누가, 얼마나), 심각도 분류(예: SEV1 전면 장애 / SEV2 주요 기능 / SEV3 부분 / SEV4 경미).
3. **선언·조직화**: 장애 채널 개설, 역할 지정.
   - **Incident Commander(IC)**: 지휘/의사결정(직접 디버깅하지 않음)
   - **Ops Lead**: 실제 조치 실행
   - **Communications Lead**: 이해관계자·고객 공지
   - **Scribe**: 타임라인 기록
4. **완화(Mitigation)**: 원인 규명보다 **영향 감소**가 우선. 롤백, 기능 플래그 OFF, 트래픽 우회/차단, 스케일 아웃, 문제 인스턴스 격리, 읽기 전용 모드.
5. **원인 파악**: 최근 변경(배포·설정·인프라), 지표/로그/추적으로 가설 → 검증. 한 번에 하나씩 변경.
6. **복구 확인**: 지표 정상화, 사용자 영향 해소, 모니터링 유지(재발 감시).
7. **종료·소통**: 해소 공지, 후속 조치 담당자 지정.
8. **포스트모템**: 사실 정리, 원인, 개선 과제.

### 1-2. 실전 팁
- 처음 5분 체크: 최근 변경? 어떤 지표가 언제부터? 영향 범위? 가장 빠른 완화 수단은?
- **변경 동결(change freeze)**: 장애 중 불필요한 변경 금지.
- 소통 주기: 15~30분마다 상태 업데이트("현재 상황/조치/다음 업데이트 시각").
- 증거 보존: 재시작 전 덤프/로그 확보 가능하면 확보.
- Runbook: 알림별 "의미 / 확인 방법 / 완화 방법 / 에스컬레이션 대상"을 한 페이지로.
- 온콜 건강: 로테이션, 인수인계, 보상, 알림 소음 관리, 새벽 알림 후 휴식 보장.
- 도구: PagerDuty/Opsgenie, Slack 전용 채널, 상태 페이지(Statuspage), 장애 타임라인 템플릿.

## 2. 포스트모템 쓰는 법

### 2-1. 원칙
- **Blameless(비난 없음)**: "누가 실수했나"가 아니라 "어떤 시스템/프로세스가 실수를 가능하게 했나". 사람 탓은 학습을 막습니다.
- 목적: 재발 방지, 조직 학습. 모든 SEV1/2는 작성, 작성 기한(예: 3~5영업일 내), 공유 및 리뷰 회의.

### 2-2. 템플릿
```
# 포스트모템: [제목] (날짜, SEV 등급)
## 요약 (3~5줄)  무엇이, 얼마나, 누구에게 영향
## 영향
- 기간: hh:mm ~ hh:mm (KST), 영향 사용자/요청 수, 매출/SLO 소진
## 타임라인 (시각, 사건, 조치)
## 근본 원인 (5 Whys / 기여 요인)
## 탐지는 어떻게 되었나 (왜 늦었나)
## 잘된 점 / 잘못된 점 / 운이 좋았던 점
## 재발 방지 조치 (Action Items)
| 조치 | 유형(예방/탐지/완화) | 담당자 | 기한 | 티켓 |
## 배운 점
```
- **5 Whys**: "왜?"를 반복해 구조적 원인(사람 → 프로세스/설계)까지.
- 조치는 **담당자·기한이 있어야** 하며 추적. 안 지켜지면 포스트모템은 일기로 끝남.
- 예방/탐지/완화 조치를 균형 있게(알림 개선, 가드레일, 자동 롤백 등).

## 3. 비용 최적화 (FinOps)

### 3-1. 접근
1. **가시성**: 태그 전략(팀/서비스/환경), 계정 분리, Cost Explorer/CUR, 예산·이상 탐지 알림, 팀별 showback/chargeback.
2. **제거**: 미사용 리소스(분리된 EBS, 오래된 스냅샷, 유휴 LB/NAT, 방치된 개발 환경), 로그 보존 정리.
3. **라이트사이징**: 사용률(CPU/메모리) 기반 인스턴스 크기 조정, 최신 세대(Graviton 등)로 전환.
4. **구매 최적화**: Savings Plans/Reserved(안정 사용량), Spot(중단 허용 워크로드), 오토스케일.
5. **아키텍처 최적화**: S3 수명주기, 데이터 전송 감소(VPC Endpoint, CDN), 캐싱, 서버리스 적합 워크로드 이동, 쿠버네티스 bin packing(Karpenter), 비업무 시간 자동 정지.
6. **문화**: 비용을 엔지니어링 지표로(서비스당 비용, 요청당 비용), 정기 리뷰.

### 3-2. 주의
- 비용 절감이 신뢰성/보안을 해치지 않게(DR/백업 삭제 금지). 변경 전 영향 분석과 롤백.
- 약정(Savings Plans)은 사용량 패턴 안정 후, 커버리지 70~80%부터.
- 성과 보고: "월 $X 절감, 연 $Y" 수치 + 리스크 평가.

## 4. 아키텍처 설계

### 4-1. 설계 프로세스
1. **요구사항**: 기능 + 비기능(가용성 SLO, 지연, 처리량, 보안/규제, 비용 한도, 팀 역량, 일정).
2. **제약/가정** 명시.
3. **후보 설계 2~3개** 비교(트레이드오프 표).
4. **결정 + 근거** → **ADR(Architecture Decision Record)** 기록.
5. **위험 분석**(단일 장애점, 병목, 보안 위협), **장애 모드** 검토.
6. **점진적 롤아웃/마이그레이션 계획**, 롤백.
7. **운영 가능성**: 모니터링, 알림, Runbook, 용량 계획, 비용.

### 4-2. 핵심 개념 체크
- 가용성(다중 AZ, 헬스체크, 용량 여유), 확장성(수평 확장, 무상태화, 캐시, 큐), 일관성/지연 트레이드오프, 복원력(타임아웃, 재시도+백오프, 서킷 브레이커, 벌크헤드), 데이터 설계(백업, PITR, RPO/RTO), 보안(최소 권한, 암호화, 격리), 단일 장애점 제거.
- **RTO**(복구 목표 시간)/**RPO**(허용 데이터 손실 시간)에 따른 DR 전략: Backup&Restore → Pilot Light → Warm Standby → Multi-site Active/Active(비용 증가).
- 복잡도는 비용: **필요한 만큼만**. 팀이 운영 못 하는 구조는 나쁜 설계.

### 4-3. ADR 템플릿
```
# ADR-012: 로그 저장소로 Loki 채택
상태: 승인 / 날짜 / 결정자
배경: ELK 비용 월 $X, 운영 부담, 검색 요구는 최근 7일 중심
옵션: (1) ELK 유지 (2) Loki (3) CloudWatch Logs
결정: Loki
근거: 비용 -60% 예상, Grafana 통합, 라벨 기반 검색으로 충분
결과/영향: 전체 텍스트 검색 약화, 보존 정책 30일, 마이그레이션 계획 링크
재검토 조건: 검색 요구 증가 시
```

## 5. 문서화
- 종류: **Runbook**(절차), **아키텍처 문서**(그림+설명, C4 모델), **ADR**, **온보딩 가이드**, **API/모듈 README**, **장애 보고서**, **FAQ**.
- 원칙: 읽는 사람이 누구인지(신입? 온콜?), "왜"를 포함, 최신성 유지(코드와 함께 Git 저장, PR에서 문서 갱신), 링크/검색 가능, 스크린샷보다 텍스트와 명령어(복붙 가능).
- Docs-as-Code(Markdown + Git + 리뷰), 다이어그램은 코드로(Mermaid, PlantUML, Diagrams).
- 문서 부채 줄이기: 장애/질문이 반복되면 문서로 전환, 분기마다 낡은 문서 정리.

## 6. 후배 가르치기 (멘토링)
- **목표**: 후배가 혼자 해결할 수 있게 만드는 것 (답을 주는 것이 아님).
- 방법:
  - 먼저 질문: "어디까지 확인했어요? 가설은?" → 사고 과정 훈련.
  - 작게 맡기고 점차 확장(읽기 전용 → 스테이징 변경 → 운영 변경 페어 → 단독).
  - 코드 리뷰는 "무엇이 틀렸나"보다 "왜 이렇게 하는 게 좋은가", 칭찬도 구체적으로. 사소한 스타일은 린터에.
  - 실패해도 안전한 환경(샌드박스, 장애 훈련/Game Day) 제공.
  - 온콜 섀도잉: 처음엔 관찰 → 보조 → 주담당.
  - 주 1회 1:1(성장 목표, 막힌 점), 학습 계획 공유.
  - 지식은 문서/세미나로 확산, 본인이 병목(single point of knowledge)이 되지 않게.
- 평가 지표: 후배의 독립 처리 범위가 넓어지는지, 같은 질문 반복이 줄어드는지.

## 7. 협업·커뮤니케이션
- **개발팀과**: 인프라를 "막는 팀"이 아닌 "돕는 플랫폼"으로. 셀프서비스 도구, 명확한 SLA, 요청 템플릿. 상호 이해(개발자의 배포 빈도 요구 vs 운영 안정성).
- **보안팀과**: 가드레일 자동화(IaC 스캔, 정책 코드)로 마찰 감소, 예외 절차 명확화.
- **경영/기획과**: 기술 이슈를 비용·위험·일정 언어로 번역. 선택지와 권고안 제시("A 안은 +$2k/월, 장애 위험 50% 감소").
- **요청 관리**: 우선순위 기준 공개(영향도/긴급도), 거절은 근거+대안과 함께, 팀 간 합의 문서화.
- **글쓰기**: 슬랙/메일은 결론 먼저, 긴 논의는 문서화, 비동기 소통 존중.
- **리뷰 문화**: 모든 변경은 PR 리뷰, 위험 변경은 설계 리뷰(RFC), 포스트모템 공유.
- 시니어 필수 소프트스킬: 설득, 갈등 조정, 한계 인정과 에스컬레이션, 우선순위/시간 관리.

## 8. 3~5년차 자가 점검표
- [ ] 장애 지휘(IC)를 맡아 복구·소통·포스트모템을 완수했다
- [ ] 비용을 분기 단위로 분석하고 절감 성과를 수치로 보고했다
- [ ] ADR을 작성하고 설계를 리뷰·승인받았다
- [ ] 팀의 Runbook/온보딩 문서를 정비했다
- [ ] 후배의 독립을 도왔다
- [ ] 비개발 직군에게 기술 이슈를 설명하고 합의를 이끌었다
- [ ] 기술 부채/위험 목록을 만들고 우선순위를 제안했다
