## A. Linux (1~10)

**Q1. 리눅스 부팅 과정을 설명해 주세요.**
전원 → BIOS/UEFI가 하드웨어 점검 후 부트로더(GRUB) 실행 → GRUB이 커널과 initramfs를 메모리에 로드 → 커널이 하드웨어 초기화 후 루트 파일시스템 마운트 → 첫 프로세스(systemd, PID 1) 실행 → 서비스(유닛)를 의존 순서대로 기동 → 로그인 프롬프트/타깃(multi-user) 도달. 부팅 문제 시 GRUB 단계, initramfs, fstab 오류 순으로 확인합니다.

**Q2. 프로세스와 스레드의 차이는?**
프로세스는 독립된 메모리 공간을 가진 실행 단위이고, 스레드는 한 프로세스 안에서 메모리(힙)를 공유하며 실행되는 흐름입니다. 스레드는 생성/전환 비용이 낮지만 공유 자원 동기화 문제가 생기고, 프로세스는 격리가 강해 안전하지만 통신(IPC)이 필요합니다.

**Q3. 좀비 프로세스란 무엇이고 어떻게 처리하나요?**
자식이 종료됐지만 부모가 종료 상태를 회수(wait)하지 않아 프로세스 테이블에 남은 상태(Z)입니다. 이미 죽었으므로 `kill`로 안 없어지고, 부모가 wait하도록 수정하거나 부모를 종료/재시작하면 init이 회수합니다. 컨테이너에서는 PID 1이 자식을 회수하지 않아 생기므로 `tini` 같은 init을 쓰거나 `--init` 옵션을 씁니다.

**Q4. `kill -9`와 `kill -15` 차이는?**
15(SIGTERM)는 프로세스가 정리 작업(연결 종료, 파일 flush)을 하도록 정상 종료를 요청하고, 9(SIGKILL)는 커널이 즉시 강제 종료하며 프로세스가 가로챌 수 없습니다. 먼저 15를 보내고 응답이 없을 때만 9를 씁니다.

**Q5. 서버가 느리다는 신고를 받았습니다. 어떻게 접근하나요?**
증상·범위·시작 시점을 확인하고 변경 이력(배포 등)을 봅니다. 서버에서 `uptime`/`top`으로 로드와 CPU, `free`로 메모리/스왑, `iostat`/`df`로 디스크 I/O와 용량, `ss`로 연결 상태, 앱 로그를 순서대로 봅니다. USE 방법(사용률/포화/에러)으로 자원별로 분리하고, 가설을 세워 하나씩 검증합니다. 임시 복구(재시작, 스케일 아웃)와 근본 원인 분석을 분리해 진행합니다.

**Q6. 디스크 여유가 있는데 파일을 만들 수 없습니다. 이유는?**
inode 고갈(`df -i`), 쿼터 초과, 읽기 전용으로 재마운트된 파일시스템(파일시스템 오류), 삭제됐지만 프로세스가 잡고 있는 파일(`lsof +L1`), 권한 문제를 의심합니다.

**Q7. 하드 링크와 심볼릭 링크의 차이는?**
하드 링크는 같은 inode를 가리키는 또 다른 이름이라 원본 삭제해도 데이터가 유지되며 파티션을 넘지 못합니다. 심볼릭 링크는 경로를 가리키는 별도 파일이라 원본이 사라지면 깨지고 파티션/디렉터리도 가리킬 수 있습니다.

**Q8. 로드 애버리지는 어떻게 해석하나요?**
실행 중이거나 대기 중인(CPU/디스크 I/O) 작업 수의 1·5·15분 평균입니다. CPU 코어 수와 비교해, 코어 4개에서 로드 4면 포화 직전입니다. 로드가 높아도 CPU 사용률이 낮다면 I/O 대기를 의심합니다.

**Q9. cron과 systemd timer의 차이는?**
cron은 단순하고 어디나 있지만 로그/의존성/실패 처리가 약합니다. systemd timer는 journald 로그, 의존성, 놓친 실행 보정(Persistent), 자원 제한을 지원합니다. 단순 작업은 cron, 서비스와 엮이는 작업은 timer를 선호합니다.

**Q10. 메모리가 부족해 OOM이 발생했습니다. 어떻게 분석하나요?**
`dmesg`/`journalctl -k`로 OOM killer 로그와 종료된 프로세스, 당시 메모리 분포를 확인합니다. 누수 vs 순간 급증 vs 설정(힙/limit) 문제를 구분하기 위해 메모리 추이 지표를 보고, 컨테이너라면 cgroup limit과 OOMKilled 이벤트를 봅니다. 대응은 limit/힙 조정, 누수 수정, 스왑/증설이고, 재발 방지로 메모리 알림을 설정합니다.

## B. 네트워크 (11~20)

**Q11. 브라우저에 URL을 입력하면 어떤 일이 일어나나요?**
URL 파싱 → 캐시 확인 → DNS 조회(캐시→리졸버→루트→TLD→권한 서버)로 IP 획득 → TCP 3-way handshake → HTTPS면 TLS handshake(인증서 검증, 키 합의) → HTTP 요청 전송 → 로드밸런서/웹서버/앱/DB 처리 → 응답 → 브라우저 렌더링(추가 리소스 요청). 각 단계에서 실패 시 증상이 달라 장애 분석에 활용됩니다.

**Q12. TCP와 UDP의 차이, 3-way handshake는 왜 3번인가요?**
TCP는 연결 지향, 순서·재전송·흐름/혼잡 제어를 제공하고, UDP는 비연결로 빠르고 가볍습니다(DNS, 스트리밍, QUIC). 3-way는 양쪽이 송수신 능력과 초기 시퀀스 번호를 확인하기 위한 최소 절차입니다(SYN → SYN/ACK → ACK). 2번이면 서버가 클라이언트가 응답을 받는지 확인할 수 없고 오래된 SYN으로 인한 잘못된 연결 위험이 있습니다.

**Q13. DNS 동작 과정과 TTL은?**
재귀 리졸버가 루트 → TLD → 권한 네임서버 순으로 질의해 레코드를 얻고 캐시합니다. TTL은 캐시 유지 시간으로, IP 변경 예정이면 미리 TTL을 낮춰 전환 후 전파 지연을 줄입니다. 장애 시 `dig +trace`로 어느 단계에서 틀어졌는지 확인합니다.

**Q14. HTTP와 HTTPS의 차이, TLS handshake 개요는?**
HTTPS는 HTTP를 TLS로 감싸 기밀성·무결성·서버 인증을 제공합니다. 핸드셰이크에서 클라이언트가 지원 암호 스위트를 보내고 서버가 인증서를 제시하면, 클라이언트가 CA 체인을 검증한 뒤 키 교환으로 세션 키를 합의하고 이후 대칭키로 암호화 통신합니다. 인증서 만료/체인 오류가 흔한 장애 원인입니다.

**Q15. L4와 L7 로드밸런서의 차이는?**
L4는 IP/포트(TCP/UDP) 기준으로 빠르게 분산(NLB), L7은 HTTP 호스트/경로/헤더 기반 라우팅과 TLS 종료, WAF 연동이 가능(ALB). 단순 TCP/초저지연/고정 IP는 L4, 마이크로서비스 경로 라우팅은 L7을 씁니다.

**Q16. 502와 504의 차이는?**
둘 다 게이트웨이/프록시가 업스트림과 통신할 때 발생합니다. 502는 업스트림이 잘못된 응답을 주거나 연결이 끊긴 경우(앱 크래시, 포트 불일치), 504는 업스트림이 제한 시간 안에 응답하지 않은 경우(느린 쿼리, 타임아웃 설정)입니다. 502는 앱 생존/헬스, 504는 지연/타임아웃 설정을 먼저 봅니다.

**Q17. 보안그룹과 NACL의 차이는?**
보안그룹은 인스턴스(ENI) 단위, 상태 저장(응답 자동 허용), 허용 규칙만 있습니다. NACL은 서브넷 단위, 상태 비저장(양방향 규칙 필요), 허용/거부 규칙과 번호 순서 평가가 있습니다. 일반적으로 보안그룹을 주 통제로 쓰고 NACL은 서브넷 수준 차단에 보조로 씁니다.

**Q18. 퍼블릭/프라이빗 서브넷의 차이와 NAT Gateway가 필요한 이유는?**
퍼블릭 서브넷은 라우팅 테이블에 IGW 경로가 있어 퍼블릭 IP로 인터넷과 직접 통신하고, 프라이빗은 없습니다. 프라이빗 인스턴스가 패치/외부 API 호출 같은 아웃바운드가 필요할 때 NAT Gateway(퍼블릭 서브넷에 위치)를 경유하며 인바운드는 차단됩니다. NAT 비용이 크므로 AWS 서비스는 VPC Endpoint로 우회해 절감합니다.

**Q19. `10.0.0.0/24`에서 사용할 수 있는 IP 수는?**
/24는 256개 주소입니다. 일반 네트워크에서 네트워크/브로드캐스트를 제외해 254개이고, AWS는 서브넷당 5개를 예약해 251개입니다.

**Q20. 서비스에 접속이 안 될 때 확인 순서는?**
범위 파악(나만? 전체?) → DNS 해석(`dig`) → 대상 도달(`ping`/`traceroute`/`mtr`) → 포트 연결(`nc -vz`/`curl -v`) → 방화벽/보안그룹/NACL/라우팅 → LB 헬스체크/타깃 상태 → 서비스 리슨 상태(`ss -tulnp`) → 앱 로그. 계층을 아래에서 위로 좁혀 갑니다.

## C. 클라우드/AWS (21~30)

**Q21. 리전과 AZ의 차이는?**
리전은 지리적으로 분리된 독립 영역(서울 등)이고, AZ는 한 리전 안의 물리적으로 분리된 데이터센터 그룹입니다. 고가용성을 위해 여러 AZ에 분산하고, 재해복구나 지연/규제 요건에는 멀티 리전을 고려합니다.

**Q22. EC2와 Lambda, 선택 기준은?**
상시 실행·긴 작업·특수 환경은 EC2(또는 컨테이너), 이벤트 기반·짧은 작업·트래픽 변동이 크거나 운영을 최소화하고 싶으면 Lambda. 지연(콜드 스타트), 15분 제한, 비용(호출량 높으면 EC2가 유리할 수 있음)을 함께 고려합니다.

**Q23. S3 스토리지 클래스와 수명주기 정책은?**
Standard(자주 접근), Intelligent-Tiering(패턴 불명), Standard-IA/One Zone-IA(드문 접근), Glacier 계열(아카이브). 예: 로그를 30일 후 IA, 90일 후 Glacier, 1년 후 삭제하는 수명주기 규칙으로 비용을 줄입니다. 최소 보관 기간/조회 비용을 확인해야 합니다.

**Q24. IAM 사용자, 그룹, 역할, 정책의 차이와 역할을 언제 쓰나요?**
사용자는 개인/장기 자격, 그룹은 사용자 묶음, 정책은 권한 문서, 역할은 임시 자격 증명으로 위임합니다. EC2/Lambda 같은 서비스, 교차 계정 접근, SSO 사용자에는 역할을 써서 장기 키를 없앱니다.

**Q25. RDS 멀티 AZ와 읽기 복제본의 차이는?**
멀티 AZ는 다른 AZ에 동기식 대기본을 두어 장애 시 자동 페일오버하는 고가용성 목적(읽기 분산 아님, 대기본은 서비스 불가). 읽기 복제본은 비동기로 읽기 트래픽 분산/확장이 목적이며 복제 지연이 있고 승격해 DR로도 쓸 수 있습니다.

**Q26. ALB와 NLB 선택 기준은?**
HTTP/HTTPS, 경로·호스트 라우팅, 인증/WAF 연동은 ALB. TCP/UDP, 초저지연·고처리량, 고정 IP/PrivateLink가 필요하면 NLB.

**Q27. AWS 비용이 갑자기 증가했습니다. 어떻게 원인을 찾나요?**
Cost Explorer로 서비스/계정/리전/태그별로 증가 항목을 분리하고, 일 단위 추이로 시작 시점을 찾아 CloudTrail/배포 이력과 대조합니다. 흔한 원인: NAT 데이터 처리, 데이터 전송, 로그 폭증, 방치된 리소스(EBS/EIP/스냅샷), 오토스케일 오작동, 공격 트래픽. 조치 후 Budgets/Anomaly Detection 알림과 태그 정책으로 재발을 방지합니다.

**Q28. 한 AZ가 장애 나도 살아남는 구조를 설명해 주세요.**
ALB를 다중 AZ에, 앱은 ASG로 최소 2개 AZ 이상에 분산, DB는 멀티 AZ(또는 Aurora), 상태는 세션 저장소/S3로 외부화, 헬스체크로 장애 인스턴스 제외, 용량은 한 AZ 손실 시에도 부하를 감당하도록 여유를 확보합니다. 실제로 AZ 장애 훈련으로 검증합니다.

**Q29. EKS와 ECS의 차이와 선택은?**
ECS는 AWS 전용 단순한 컨테이너 오케스트레이션(운영 부담 적음, Fargate와 궁합), EKS는 표준 쿠버네티스(생태계/이식성/강력한 확장, 대신 학습·운영 복잡도와 컨트롤 플레인 비용). 팀이 K8s 역량/요구(Helm, 오퍼레이터, 멀티클라우드)가 있으면 EKS, 단순 서비스는 ECS.

**Q30. 온프레미스 시스템을 클라우드로 마이그레이션하는 접근법은?**
6R(Rehost, Replatform, Refactor, Repurchase, Retire, Retain) 중 워크로드별 선택. 현황 파악(의존성, 데이터량) → 파일럿 → 네트워크 연결(VPN/Direct Connect) → 데이터 이관(DMS, 스냅샷) → 컷오버 계획(롤백 포함) → 검증 → 비용·보안 최적화 순으로 진행합니다.

## D. Python/Bash/Git (31~35)

**Q31. `merge`와 `rebase`의 차이와 사용 기준은?**
merge는 두 브랜치를 합쳐 머지 커밋을 만들고 이력을 보존, rebase는 내 커밋을 대상 브랜치 끝으로 재배치해 선형 이력을 만듭니다. 공유된(이미 푸시된) 브랜치는 rebase하지 않고, 로컬 기능 브랜치 정리에는 rebase를 씁니다.

**Q32. 실수로 비밀키를 GitHub에 커밋했습니다. 어떻게 하나요?**
1순위는 키를 즉시 폐기/교체(rotate)하고 CloudTrail 등으로 사용 이력을 조사합니다. 이력에서 제거(`git filter-repo`/BFG)는 그 다음이며 이미 유출됐다고 가정합니다. 재발 방지로 pre-commit gitleaks, 시크릿 스캐닝, 시크릿 매니저 사용을 적용합니다.

**Q33. Bash의 `set -euo pipefail`은 무엇인가요?**
`-e` 명령 실패 시 종료, `-u` 정의되지 않은 변수 사용 시 오류, `-o pipefail` 파이프 중간 실패도 실패로 취급. 스크립트가 오류를 조용히 지나쳐 위험한 작업을 계속하는 것을 막습니다. 단 `-e`의 예외 동작을 알고 중요한 곳은 명시적으로 검사합니다.

**Q34. 멱등성이란 무엇이고 자동화에서 왜 중요한가요?**
같은 작업을 여러 번 실행해도 결과가 같은 성질입니다. 재시도·재실행 시 중복 생성/오류를 막고 자동화를 안전하게 합니다. 예: `mkdir -p`, Ansible 모듈, Terraform 선언형, 스크립트에서 "있으면 건너뜀" 검사.

**Q35. Python으로 자동화한 경험을 말씀해 주세요.**
(구조) 문제 → 접근 → 구현 → 안전장치 → 결과. 예: "태그 없는 EC2와 미사용 EBS를 찾는 boto3 스크립트를 만들어 `--dry-run`, 슬랙 리포트를 추가했고, 주간 리포트로 월 약 $N 절감 후보를 찾았습니다. 삭제는 자동화하지 않고 담당자 확인을 거치게 설계했습니다."

## E. 컨테이너/쿠버네티스 (36~45)

**Q36. 컨테이너와 VM의 차이는?**
VM은 하이퍼바이저 위에 게스트 OS 전체를 올려 강한 격리와 무거움, 컨테이너는 호스트 커널을 공유하고 namespace/cgroup으로 격리해 가볍고 빠릅니다. 커널 공유라 격리 수준은 낮아 보안 설정(비루트, seccomp 등)이 중요합니다.

**Q37. Docker 이미지 크기를 줄이고 빌드를 빠르게 하는 방법은?**
슬림/distroless 베이스, 멀티스테이지 빌드, 불필요 파일 제외(.dockerignore), RUN 합치고 캐시 정리, 변경 적은 레이어를 위에(의존성 설치 → 소스 복사 순), BuildKit 캐시. 효과는 이미지 크기·빌드 시간 수치로 확인합니다.

**Q38. `CMD`와 `ENTRYPOINT`의 차이는?**
ENTRYPOINT는 컨테이너의 고정 실행 파일, CMD는 기본 인자/기본 명령(실행 시 덮어쓰기 쉬움). 보통 ENTRYPOINT에 실행 파일, CMD에 기본 옵션을 두고, exec 형식(JSON 배열)으로 써서 시그널이 PID 1 프로세스에 전달되게 합니다.

**Q39. Pod가 CrashLoopBackOff일 때 어떻게 디버깅하나요?**
`kubectl describe pod`로 이벤트/종료 코드/OOMKilled 확인 → `kubectl logs --previous`로 직전 크래시 로그 → 설정(ConfigMap/Secret/환경변수), 의존 서비스 접근, 시작 명령, probe 설정(너무 빠른 liveness), 리소스 limit을 점검 → 필요 시 `kubectl debug`/동일 이미지에 셸로 재현합니다.

**Q40. Deployment, StatefulSet, DaemonSet의 차이는?**
Deployment는 상태 없는 앱의 복제본 관리(롤링 업데이트), StatefulSet은 고정 이름·순서·전용 볼륨이 필요한 상태 저장 앱(DB), DaemonSet은 모든(또는 특정) 노드마다 하나씩(로그/모니터링 에이전트).

**Q41. Service 타입(ClusterIP/NodePort/LoadBalancer)의 차이는?**
ClusterIP는 클러스터 내부 가상 IP, NodePort는 각 노드의 고정 포트로 외부 노출, LoadBalancer는 클라우드 LB를 프로비저닝해 외부 노출합니다. HTTP는 보통 Ingress로 하나의 LB 뒤에서 경로/호스트 라우팅합니다.

**Q42. liveness와 readiness probe의 차이는?**
liveness 실패는 컨테이너 재시작, readiness 실패는 Service 엔드포인트에서 제외(트래픽 차단, 재시작 안 함). 느린 초기화 앱은 startup probe를 써서 liveness가 조기 실패시키지 않게 합니다. liveness에 외부 의존성을 넣으면 연쇄 재시작이 일어날 수 있어 피합니다.

**Q43. requests와 limits의 차이, 초과하면 어떻게 되나요?**
requests는 스케줄링 기준·보장량, limits는 상한. CPU limit 초과는 스로틀링(느려짐), 메모리 limit 초과는 OOMKilled. requests를 너무 낮추면 노드 과밀과 성능 저하, 너무 높으면 낭비이므로 실제 사용량 기반으로 조정합니다(VPA/모니터링).

**Q44. 쿠버네티스에서 무중단 배포를 어떻게 구현하나요?**
RollingUpdate(maxUnavailable/maxSurge) + readiness probe로 준비된 Pod만 트래픽 수신, `preStop` 훅/종료 유예 시간으로 진행 중 요청 처리, PodDisruptionBudget, 하위 호환 가능한 DB 마이그레이션(확장→전환→정리). 고위험 변경은 카나리/블루그린을 씁니다.

**Q45. Kubernetes Secret은 안전한가요? 어떻게 관리하나요?**
기본 Secret은 base64 인코딩일 뿐 암호화가 아니며, etcd 암호화(at-rest)와 RBAC 제한이 필요합니다. 더 안전하게는 External Secrets Operator/CSI Driver로 Secrets Manager/Vault와 연동하거나 Sealed Secrets/SOPS로 Git에 암호화 저장하고, 가능한 한 로그/환경변수 노출을 피합니다.

## F. IaC/CI-CD (46~52)

**Q46. IaC를 쓰는 이유는?**
재현성(환경 복제), 변경 이력/리뷰, 사람 실수 감소, 자동화·속도, 드리프트 감지, 문서화 효과. 장애 시 동일 환경 재구축이 쉬워집니다.

**Q47. Terraform state는 무엇이고 왜 원격 백엔드와 락을 쓰나요?**
state는 코드와 실제 리소스를 매핑한 기록입니다. 로컬 파일은 유실/공유 불가이고 동시 apply 시 충돌·손상 위험이 있어 S3 등 원격 백엔드와 락(DynamoDB 등)을 씁니다. state에 비밀값이 포함될 수 있어 암호화·접근 제한이 필요합니다.

**Q48. `terraform plan`에서 의도치 않은 destroy가 보이면 어떻게 하나요?**
apply하지 않고 원인을 파악합니다: 리소스 이름/주소 변경(`moved` 블록, `state mv`로 해결), `count/for_each` 키 변화, 변수 변경, provider 버전 영향. 중요한 리소스에는 `prevent_destroy`를 두고, 팀에서는 plan 리뷰/승인 후 apply 절차를 지킵니다.

**Q49. 드리프트란? 어떻게 감지하고 대응하나요?**
코드와 실제 인프라가 달라진 상태(주로 콘솔 수동 변경). 정기 `plan`(또는 CI 스케줄), AWS Config, 드리프트 감지 도구로 발견하고, 변경이 정당하면 코드에 반영, 아니면 apply로 되돌립니다. 근본적으로는 콘솔 쓰기 권한을 줄이는 것입니다.

**Q50. CI와 CD의 차이, Delivery와 Deployment의 차이는?**
CI는 코드 통합 시 자동 빌드·테스트, CD는 배포 자동화. Continuous Delivery는 배포 가능 상태까지 자동화하고 운영 배포는 승인, Continuous Deployment는 승인 없이 운영까지 자동 배포합니다.

**Q51. 배포 전략(Rolling, Blue/Green, Canary)을 비교해 주세요.**
Rolling은 점진 교체(추가 자원 적음, 롤백 느림), Blue/Green은 새 환경을 만들어 전환(즉시 롤백 가능, 자원 2배), Canary는 소량 트래픽으로 검증 후 확대(위험 최소, 메트릭 기반 자동화 필요). 변경 위험도와 비용에 따라 선택합니다.

**Q52. CI/CD에서 비밀값은 어떻게 관리하고 OIDC란?**
CI의 시크릿 저장소에 두되 로그 노출을 막고 최소 권한으로 제한합니다. 더 좋은 방법은 OIDC로 CI가 발급받은 단기 토큰으로 클라우드 역할을 맡아 장기 키 자체를 없애는 것입니다. 포크 PR에서 시크릿 접근을 제한하고 서드파티 액션은 버전/SHA 고정합니다.

## G. 모니터링/SRE/보안 (53~60)

**Q53. 모니터링과 관측성의 차이는?**
모니터링은 사전에 정의한 지표/알림으로 알려진 문제를 감시, 관측성은 지표·로그·추적 데이터로 처음 보는 문제도 질문하며 원인을 찾을 수 있는 능력입니다.

**Q54. SLI, SLO, SLA, 에러 버짓을 설명해 주세요.**
SLI는 측정 지표(성공 요청 비율), SLO는 내부 목표(30일 99.9%), SLA는 고객과의 계약(위반 시 보상). 에러 버짓은 허용 실패량(99.9%면 월 약 43분)으로, 소진되면 신규 배포를 줄이고 안정화에 투자하는 의사결정 도구입니다.

**Q55. 알림이 너무 많이 울릴 때(알림 피로) 어떻게 개선하나요?**
알림을 사용자 영향 기반(증상)으로 재정비하고, 조치 불필요한 알림은 제거/티켓으로 강등, 임계치와 `for` 지속 시간 조정, 중복 묶기/억제, Runbook과 담당자 명시, 월간 알림 리뷰(조치율 측정)를 합니다.

**Q56. 평균 응답시간 대신 p99를 보는 이유는?**
평균은 소수의 느린 요청을 가립니다. 사용자는 느린 경험에 민감하고 분산 시스템에서는 꼬리 지연이 전체에 영향을 주므로 p95/p99를 SLI로 씁니다. 히스토그램 지표가 필요합니다.

**Q57. 새벽에 알림이 왔습니다. 처음 5분간 무엇을 하나요?**
알림 확인(인지 표시) → 사용자 영향 범위/심각도 판단 → 최근 배포·변경 확인 → 대시보드로 증상 확인 → 가장 빠른 완화(롤백, 스케일, 우회) 시도 → 필요 시 에스컬레이션/장애 채널 개설과 상황 공유 → 원인 분석은 완화 후. 모든 조치를 타임라인으로 기록합니다.

**Q58. 장애 시 원인 분석과 복구 중 무엇이 우선인가요?**
복구(사용자 영향 최소화)가 우선입니다. 롤백·트래픽 전환 같은 완화를 먼저 하고, 증거(로그, 지표, 덤프)는 보존하되 사후 분석에서 근본 원인을 밝혀 재발 방지책을 만듭니다.

**Q59. AWS 액세스 키가 유출된 것 같습니다. 대응 절차는?**
키 비활성화/삭제(교체) → 해당 키의 CloudTrail 이력 조사(생성된 리소스, 권한 변경, 데이터 접근) → 의심 리소스·백도어 IAM/키 제거 → 영향 범위 파악·보고 → 재발 방지(SSO/역할 전환, 시크릿 스캐닝, 최소 권한). 비용 이상(채굴)도 확인합니다.

**Q60. 최소 권한 원칙을 어떻게 실천하나요?**
처음엔 필요한 권한만 부여(리소스·조건 한정, `*` 지양), 사람은 SSO+임시 자격, 서비스는 역할, 접근 분석기/마지막 사용 정보로 미사용 권한 회수, IaC로 정책을 코드 리뷰, 멀티 계정과 SCP로 상한 설정, break-glass는 감사 알림과 함께 운영합니다.
