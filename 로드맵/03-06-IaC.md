# 03-06. IaC (Terraform, Ansible)

> **IaC(Infrastructure as Code)**: 서버·네트워크 같은 인프라를 콘솔 클릭 대신 코드로 정의하고 Git으로 관리하는 방식. 장점: 재현성, 변경 이력, 리뷰 가능, 자동화, 환경 복제.

## 1. 개념 설명

### 1-1. 선언형 vs 절차형, Terraform vs Ansible
| 구분 | Terraform | Ansible |
|---|---|---|
| 주 용도 | 인프라 **생성/프로비저닝**(VPC, EC2, RDS...) | 서버 **설정/구성 관리**(패키지, 파일, 서비스) |
| 방식 | 선언형(원하는 최종 상태 기술), 상태(state) 파일 보유 | 절차+멱등 모듈(playbook), 에이전트 없이 SSH |
| 언어 | HCL | YAML |
| 조합 | Terraform으로 서버 생성 → Ansible로 서버 설정 (요즘은 컨테이너/이미지로 대체되는 경향) |
- **멱등성**: 같은 코드를 여러 번 실행해도 결과가 같은 성질.
- **불변 인프라**: 서버를 고치지 않고 새 이미지로 교체(Packer, 컨테이너).

### 1-2. Terraform
- 워크플로: `terraform init`(플러그인 다운로드) → `plan`(변경 미리보기) → `apply`(적용) → `destroy`(삭제). `fmt`, `validate`.
- 구성요소: **provider**(AWS 등 연결), **resource**(만들 것), **data**(기존 것 조회), **variable/output/locals**, **module**(재사용 단위), **backend**(state 저장소).
- **State**: Terraform이 "내가 관리하는 실제 리소스 목록"을 기록한 파일. 유실/충돌하면 재앙 → **S3 + DynamoDB 락(또는 S3 네이티브 락)** 같은 원격 백엔드, 팀 작업 시 필수. state에 비밀값이 들어갈 수 있음 → 암호화, 접근 제한.
- 의존성: 암시적(참조) / 명시적(`depends_on`). `count`, `for_each`, 동적 블록, `lifecycle`(`prevent_destroy`, `create_before_destroy`, `ignore_changes`).
- **import**: 기존 리소스를 state로 가져오기. **drift**: 코드와 실제 상태 불일치(콘솔 수동 변경 때문).
- 환경 분리: 디렉터리 분리(dev/stage/prod) + 모듈 권장(워크스페이스는 신중). 도구: Terragrunt, Atlantis(PR 기반 apply), tflint, tfsec/Checkov(보안 검사), Infracost(비용 예측).
- OpenTofu: Terraform 라이선스 변경 후 나온 오픈소스 포크. 문법 거의 동일.
- 예시:
```hcl
resource "aws_s3_bucket" "logs" {
  bucket = "my-logs-${var.env}"
}
resource "aws_s3_bucket_public_access_block" "logs" {
  bucket                  = aws_s3_bucket.logs.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}
```

### 1-3. Ansible
- **인벤토리**(대상 서버 목록), **플레이북**(할 일 YAML), **태스크/모듈**(`apt`, `copy`, `template`, `service`), **롤(role)**(재사용 단위), **변수/Jinja2 템플릿**, **handler**(변경 시 재시작), **vault**(비밀 암호화), **조건/반복**.
- 실행: `ansible-playbook -i inventory site.yml --check --diff`(드라이런).
- 사용처: 서버 초기 설정(SSH, 사용자, 패키지), 보안 하드닝, 패치 롤링 적용, 온프레미스 관리, 네트워크 장비.
- 예시:
```yaml
- hosts: web
  become: true
  tasks:
    - name: nginx 설치
      ansible.builtin.apt: { name: nginx, state: present, update_cache: true }
    - name: 서비스 시작
      ansible.builtin.service: { name: nginx, state: started, enabled: true }
```

### 1-4. 운영 모범 사례
- 콘솔에서 수동 변경 금지(또는 최소화), 모든 변경은 PR → plan 결과 리뷰 → apply.
- 비밀값은 코드/tfvars에 넣지 않음(Secrets Manager/SSM, 환경변수, Vault).
- 모듈 버전 고정, provider 버전 고정(`.terraform.lock.hcl` 커밋).
- 삭제 방지(`prevent_destroy`), plan에서 destroy 항목 주의 깊게 확인.

## 2. 공부 순서
Terraform: 기본 문법 → 변수/출력 → state·백엔드 → 모듈 → VPC/EC2/RDS 전체 구성 → 환경 분리 → CI 연동(PR plan, 승인 후 apply) → 정책/보안 스캔 → import/drift 대응.
Ansible: 인벤토리·ad-hoc → 플레이북 → 롤 → 템플릿 → 핸들러 → Vault → 파이프라인 연동.
- 기간: Terraform 3주(+ Associate 시험 준비 2주), Ansible 1~2주.

## 3. 실습 과제
1. Terraform으로 EC2 1대 + SG 생성/삭제 반복.
2. S3 + DynamoDB로 원격 state 구성 → 두 사람이 동시에 apply 시도 시 락 확인.
3. VPC 모듈 직접 작성(퍼블릭/프라이빗 서브넷 2AZ, NAT, 라우팅) 후 `dev`/`prod`에서 재사용.
4. ALB + ASG + RDS까지 코드로 구성(프로젝트 4).
5. 콘솔에서 SG 규칙을 수동 변경 → `plan`으로 drift 확인 → 복구.
6. 기존에 콘솔로 만든 S3를 `import`.
7. GitHub Actions에서 PR 시 `plan` 결과 코멘트, tfsec/Checkov 실패 시 머지 차단.
8. Ansible 롤로 서버 5대에 nginx+보안 설정 적용, `--check`로 변경 미리보기.
9. (심화) Packer로 AMI 만들고 Terraform에서 사용 / Terraform으로 EKS 생성(비용 주의).
