# 03-08. 모니터링·로깅 (Prometheus, Grafana, ELK, 알림, 장애 대응)

## 1. 개념 설명

### 1-1. 관측성의 3대 신호
- **지표(Metrics)**: 숫자 시계열(CPU, 요청 수, 지연시간). 가볍고 추세/알림에 적합.
- **로그(Logs)**: 이벤트 기록. 상세하지만 양이 큼.
- **추적(Traces)**: 요청 하나가 여러 서비스를 거치는 경로와 시간(Jaeger, Tempo, OpenTelemetry).
- **모니터링**: 알려진 문제를 감시. **관측성**: 모르는 문제도 질문해서 파악할 수 있는 능력.

### 1-2. 무엇을 볼 것인가
- **골든 시그널(Google SRE)**: 지연(Latency), 트래픽(Traffic), 에러(Errors), 포화(Saturation).
- **RED**(서비스): Rate, Errors, Duration. **USE**(자원): Utilization, Saturation, Errors.
- **SLI**(측정 지표, 예: 성공 요청 비율) → **SLO**(목표, 예: 30일 99.9%) → **SLA**(고객과의 계약). **에러 버짓**: 허용되는 실패량(99.9%면 월 약 43분). 버짓 소진 시 기능 개발보다 안정화 우선.
- **백분위 지연시간**: 평균은 속임. p50/p95/p99를 본다.

### 1-3. Prometheus
- 오픈소스 지표 수집/저장 시스템. **pull 방식**: 대상(`/metrics`)을 주기적으로 긁어옴. 구성: Prometheus 서버, **exporter**(node_exporter, kube-state-metrics, blackbox), **Alertmanager**(알림 라우팅/묶기/억제), **서비스 디스커버리**.
- 지표 타입: Counter(증가만), Gauge(오르내림), Histogram/Summary(분포).
- **PromQL** 예시: `rate(http_requests_total{status=~"5.."}[5m]) / rate(http_requests_total[5m])` (5xx 비율), `histogram_quantile(0.99, sum(rate(http_request_duration_seconds_bucket[5m])) by (le))`.
- 주의: **카디널리티**(라벨 값 종류 폭발, user_id 같은 라벨 금지). 장기 저장은 Thanos/Mimir/VictoriaMetrics.
- 알림 규칙 예: `expr: up == 0, for: 5m`.

### 1-4. Grafana
- 시각화/대시보드. 데이터 소스(Prometheus, Loki, Elasticsearch, CloudWatch). 변수, 알림, 대시보드를 JSON/코드(Terraform, Grafana provisioning)로 관리.
- 좋은 대시보드: 위에서 아래로 "서비스 건강 → 원인 후보 → 상세", 한 화면에 목적 하나, 임계선 표시.

### 1-5. 로깅 스택
- **ELK/EFK**: Elasticsearch(저장/검색) + Logstash 또는 Fluentd/Fluent Bit(수집) + Kibana(시각화). 강력하지만 자원 비용 큼.
- **Loki + Promtail/Alloy**: 로그를 라벨 중심으로 저렴하게 저장, Grafana에서 조회. 쿠버네티스에 가볍게 적합.
- 클라우드 관리형: CloudWatch Logs/Insights, OpenSearch.
- 모범 사례: **구조화 로그(JSON)**, 로그 레벨, 요청 ID(상관관계 ID) 전파, 개인정보·비밀값 마스킹, 보존 기간·비용 정책, 샘플링.
- **OpenTelemetry**: 지표/로그/추적을 표준 방식으로 수집하는 벤더 중립 프레임워크.

### 1-6. 알림 설계
- 원칙: **사람이 즉시 조치해야 하는 것만 호출(page)**. 나머지는 티켓/슬랙. 증상 기반 알림(사용자 영향) 우선, 원인 기반(CPU 80%)은 보조.
- **알림 피로(alert fatigue)** 방지: 임계치·`for` 지속시간 조정, 중복 묶기, 억제, 담당자/Runbook 링크 포함.
- 알림 메시지 필수 요소: 무엇이, 어디서, 얼마나 심각, 영향, 대응 문서 링크.
- 도구: PagerDuty, Opsgenie, Slack, Grafana OnCall. **온콜**: 당번 순환, 에스컬레이션 정책, 인수인계.
- 가용성 외부 감시: Blackbox exporter, UptimeRobot, Synthetic 모니터링.

### 1-7. 장애 대응 개요 (상세는 [07번](07-실무역량.md))
- 흐름: 탐지 → 선언/심각도 분류 → 완화(우선: 복구, 원인분석은 나중) → 소통 → 해결 → 포스트모템.
- 완화 수단: 롤백, 기능 플래그 끄기, 트래픽 우회, 스케일 아웃, 의존 서비스 차단.
- 지표: MTTD(탐지), MTTA(인지), MTTR(복구).

## 2. 공부 순서
Linux/클라우드 기본 지표 → Prometheus+node_exporter → PromQL → Grafana 대시보드 → Alertmanager → 로깅(Loki 또는 ELK) → 쿠버네티스 모니터링(kube-prometheus-stack) → SLI/SLO → OpenTelemetry/추적 → 온콜/포스트모템.
- 기간: 4주 + 업무 중 지속.

## 3. 실습 과제
1. VM에 node_exporter + Prometheus + Grafana(docker compose)로 서버 대시보드.
2. 샘플 앱에 `/metrics` 추가(`prometheus_client`), 요청 수·지연 시간 히스토그램 노출.
3. PromQL로 5xx 비율, p99 지연시간 그래프 작성.
4. "디스크 85% 5분 지속" 알림 → Slack 전송, 메시지에 Runbook 링크.
5. 알림이 울리게 장애 주입(디스크 채우기, 프로세스 kill, 부하) → 대응 → 포스트모템 1페이지.
6. kube-prometheus-stack을 Helm으로 설치, Pod 재시작 횟수/OOM 알림 구성.
7. Loki로 로그 수집 → 에러 로그 급증 패널 → 로그에서 요청 ID로 추적.
8. SLO 정의: "30일 가용성 99.9%" → 에러 버짓 소진율 대시보드/알림(번 레이트).
9. (심화) OpenTelemetry로 두 서비스 간 분산 추적 Jaeger/Tempo에서 확인.
10. (심화) 카디널리티 폭발을 일부러 일으키고 원인 제거.
