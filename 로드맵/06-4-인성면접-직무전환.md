# 06-4. 인성 면접: "왜 직무를 바꾸는가" 외 답변 예시

## 1. 전직 답변의 공식
**과거(전 직무에서 발견한 것) → 계기(이 분야를 알게 된 구체적 사건) → 준비(실제로 한 일) → 연결(이 회사/직무에서 기여할 점)**
- 피할 것: 전 직무/회사 험담, "그냥 연봉이 높아서", "유망해서", 막연한 열정.
- 포함할 것: 구체적 에피소드, 학습 증거(프로젝트·자격증), 전 직무 경험의 연결, 장기 방향.

## 2. "왜 직무를 바꾸시나요?" 예시 (배경별)

### 예시 A: 개발자 → DevOps/클라우드
"백엔드 개발자로 일하면서 가장 보람을 느낀 순간이 기능 배포보다 배포 파이프라인을 개선했을 때였습니다. 수동으로 1시간 걸리던 배포를 스크립트와 CI로 10분으로 줄이자 팀의 배포 빈도가 올라갔고, 그때부터 코드가 사용자에게 안정적으로 전달되는 전체 흐름에 관심이 생겼습니다. 이후 1년간 AWS, Terraform, Kubernetes를 학습하며 3-tier 인프라 코드화와 GitOps 배포 프로젝트를 만들고 AWS SAA를 취득했습니다. 개발 경험 덕분에 개발팀의 어려움을 이해하며 배포와 운영을 개선할 수 있다고 생각해 지원했습니다."

### 예시 B: 시스템/네트워크 운영자(온프레미스, SI) → 클라우드
"온프레미스 서버를 운영하며 서버 증설에 몇 주가 걸리고 장애 대응이 수작업에 의존하는 한계를 반복해서 겪었습니다. 클라우드와 IaC로 같은 일을 몇 분에 재현할 수 있다는 걸 알고, 퇴근 후 AWS와 Terraform을 학습하며 기존 구성을 코드화해 보았습니다. 서버 패치를 Ansible로 자동화해 작업 시간을 70% 줄인 경험도 있습니다. 쌓아 온 Linux·네트워크 운영 경험에 클라우드 자동화를 결합해, 안정성과 속도를 함께 높이는 엔지니어가 되고자 지원했습니다."

### 예시 C: 비 IT(영업/CS/운영/사무 등) → 인프라
"서비스 운영/고객 응대를 하면서 장애로 고객이 불편을 겪을 때 뒤에서 이를 해결하는 엔지니어의 역할에 흥미를 느꼈습니다. 직접 해 보고 싶어 Linux와 AWS를 독학하고 6개월간 5개 프로젝트를 구축했습니다. 비 IT 경험은 약점이 아니라 '서비스 장애가 사용자에게 어떤 영향을 주는지'를 현장에서 본 경험이며, 고객 중심으로 우선순위를 판단하고 비개발 직군과 소통하는 데 강점이 됩니다. 기술 기본기는 프로젝트와 자격증으로 증명했고, 입사 후에도 빠르게 학습하겠습니다."

### 예시 D: 데이터/분석 → MLOps
"데이터 분석가로 모델을 만들었지만 운영에 올리지 못하고 노트북에서 끝나는 경우가 반복됐습니다. 모델을 재현 가능하게 배포하고 모니터링하는 MLOps에 관심이 생겨 Docker, Kubernetes, MLflow를 학습하고, 학습-배포-드리프트 감지 파이프라인 프로젝트를 구현했습니다. 데이터와 모델의 특성을 이해하는 점이 인프라 설계에서 강점이 된다고 생각합니다."

### 예시 E: QA/테스트 → DevOps
"QA로서 릴리스 때마다 수동 회귀 테스트와 환경 불일치로 일정이 지연되는 문제를 겪었습니다. 테스트 자동화를 CI에 붙여 릴리스 검증 시간을 줄인 경험이 계기가 되어 파이프라인과 환경 관리 전반을 다루는 DevOps로 전환하고자 합니다. 품질과 안정성에 대한 관점이 배포 안정화에 기여할 수 있다고 생각합니다."

## 3. 전직 관련 후속 질문 대비
- **"직무가 안 맞으면 또 바꾸지 않을까요?"** → 이번 선택의 근거(학습·프로젝트에 투자한 시간과 비용, 작은 성공 경험)를 제시. "시도해 보고 확신이 생겼기 때문에 구체적인 증거를 만들었다."
- **"연봉이 줄어도 괜찮나요?"** → 장기적 성장 중시, 현실적 기대치 이해, 1~2년 내 성과로 증명하겠다. (거짓으로 아무 조건이나 수용하지는 말 것)
- **"경력이 없는데 왜 뽑아야 하나요?"** → 기술 기본기(자격증/프로젝트), 학습 속도(스터디/블로그), 운영 마인드(문서화/안전 습관), 전 직무 도메인 이해. 구체적 사례 1개.
- **"입사 후 3개월/1년/5년 목표는?"** → 3개월: 시스템 파악/Runbook 작성/1차 대응, 1년: 담당 영역 자동화·개선 1건, 5년: 한 분야 전문성과 설계·후배 육성.

## 4. 공통 인성 질문 예시 답변 틀

**자기소개(1분)**: 현재 정체성(전직 배경) → 전환 계기 → 준비한 것(수치) → 지원 동기 한 줄.
**장점/단점**: 장점은 직무와 연결(꼼꼼한 문서화, 문제 끝까지 추적, 학습 속도). 단점은 극복 행동과 함께(예: "한 문제를 오래 붙잡는 편이라 2시간 규칙을 만들어 질문/우회를 합니다").
**실패/갈등 경험**: 사실 → 내 책임 → 조치 → 배운 점 → 재발 방지. 인프라에선 "실수를 숨기지 않고 공유해 재발 방지 절차를 만든 경험"이 높게 평가됩니다.
**장애/압박 상황 경험**: 침착, 우선순위(복구 먼저), 소통(상황 공유), 사후 개선.
**협업 스타일**: 개발자·보안·기획과의 소통, 문서화, 요청을 거절하거나 조율한 경험.
**야근/온콜**: 필요성을 이해하되 지속 가능한 구조(자동화, 로테이션)를 만들고자 하는 태도. 조건은 솔직하게 확인.
**지원 동기(회사별)**: 회사 블로그/제품/기술 스택의 구체적 포인트 + 내 경험의 연결.
**역질문**: 팀 구성/온콜 구조/최근 가장 큰 장애와 개선/신입 온보딩 방식/기술 부채 관리.

## 5. 면접 매너
- 답변은 1~2분, 두괄식. 모르면 모른다고 하고 사고 과정을 설명.
- 거짓 경험 금지(꼬리 질문에서 무너짐). 팀 프로젝트는 "내 역할"을 명확히.
- 화상 면접 환경(조용한 곳, 마이크, 화면 공유 테스트) 점검, 메모는 키워드만.
- 면접 후 24시간 내 복기 노트: 못 답한 질문, 면접관 반응, 배운 점.
