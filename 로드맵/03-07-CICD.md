# 03-07. CI/CD (GitHub Actions, Jenkins, ArgoCD)

## 1. 개념 설명

### 1-1. 기본 개념
- **CI(Continuous Integration, 지속적 통합)**: 코드를 자주 합치면서 자동으로 빌드·테스트·린트를 돌려 문제를 빨리 발견.
- **CD**: Continuous **Delivery**(배포 가능한 상태까지 자동, 운영 배포는 사람 승인) / Continuous **Deployment**(운영까지 완전 자동).
- **파이프라인**: 코드 푸시 → 빌드 → 테스트 → 보안 스캔 → 이미지 생성 → 레지스트리 푸시 → 배포 → 검증 → (실패 시) 롤백.
- 배포 전략: **Rolling**(조금씩 교체), **Blue/Green**(새 환경 만들어 한 번에 전환), **Canary**(일부 트래픽만 먼저), **Feature Flag**. 롤백 계획이 없으면 배포 자동화가 아니라 사고 자동화.
- **아티팩트**: 빌드 결과물(이미지, 패키지). 한 번 빌드한 결과물을 환경 이동 시 그대로 승급(build once, deploy many).
- 브랜치 전략: GitHub Flow(main + 기능 브랜치), trunk-based(작은 변경을 자주 main에).

### 1-2. GitHub Actions
- 구성: **workflow**(.github/workflows/*.yml) → **event**(push, pull_request, schedule, workflow_dispatch) → **job**(러너에서 실행) → **step**(`uses:` 액션 또는 `run:` 명령).
- 핵심: `secrets`, `env`, `matrix`(여러 버전 병렬), `cache`, `needs`(잡 의존), `environments`(승인 규칙), `concurrency`, 재사용 워크플로, self-hosted runner.
- **OIDC**: 장기 액세스 키 대신 GitHub이 발급한 토큰으로 AWS 역할 임시 사용 → 키 유출 위험 제거.
- 보안: 서드파티 액션은 커밋 SHA로 고정, `permissions:` 최소화, PR 포크에서 시크릿 노출 주의.
```yaml
name: ci
on: [pull_request]
permissions: { contents: read }
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12" }
      - run: pip install -r requirements.txt && pytest
```

### 1-3. Jenkins
- 오래된 오픈소스 자동화 서버. 한국 기업/SI에서 아직 매우 많이 사용.
- 구성: Controller(관리) + Agent(실행), **Jenkinsfile**(Pipeline as Code, Declarative/Scripted), 플러그인 생태계, Credentials, Shared Library.
- 장점: 자유도, 온프레미스. 단점: 플러그인 의존·유지보수·보안 패치 부담, UI 설정 → 코드화 필수.
- 운영 포인트: Agent를 동적(쿠버네티스 Pod)으로, 백업, 접근 제어, 플러그인 최소화.
```groovy
pipeline {
  agent any
  stages {
    stage('Build') { steps { sh 'docker build -t app:${GIT_COMMIT} .' } }
    stage('Test')  { steps { sh 'pytest' } }
    stage('Deploy'){ when { branch 'main' } steps { sh './deploy.sh' } }
  }
}
```

### 1-4. ArgoCD와 GitOps
- **GitOps**: "원하는 상태"를 Git에 선언하고, 에이전트가 클러스터 상태를 Git과 일치시킴. 장점: 변경 이력/리뷰/롤백이 Git으로 해결, 클러스터 자격증명을 CI에 두지 않아도 됨(pull 방식).
- **ArgoCD**: 쿠버네티스용 GitOps 도구. **Application**(Git 경로↔클러스터/네임스페이스), 동기화 상태(Synced/OutOfSync, Healthy), auto-sync/self-heal/prune, **App of Apps/ApplicationSet**, Helm/Kustomize 지원, Argo Rollouts(카나리/블루그린), Image Updater.
- 권장 구조: 앱 코드 저장소(CI: 테스트·이미지 빌드·푸시) + **매니페스트(환경) 저장소**(CI가 이미지 태그만 갱신하는 PR/커밋) → ArgoCD가 반영.
- 대안: Flux, Spinnaker, GitLab CI, CircleCI, AWS CodePipeline, Tekton.

### 1-5. 품질/보안 게이트(DevSecOps)
- 린트, 단위/통합 테스트, SAST(SonarQube), 의존성 스캔(Dependabot, Snyk), 이미지 스캔(Trivy), 시크릿 스캔(gitleaks), IaC 스캔(Checkov), 서명(cosign), SBOM.
- 지표(DORA): 배포 빈도, 변경 리드타임, 변경 실패율, 복구 시간(MTTR).

## 2. 공부 순서
Git/브랜치 전략 → GitHub Actions 기본(린트/테스트) → Docker 빌드/푸시 → 클라우드 배포(OIDC) → 환경 분리·승인 → Jenkins 기본 → 보안 스캔 통합 → Helm/Kustomize → ArgoCD GitOps → 배포 전략(카나리) → DORA 지표.
- 기간: 4주.

## 3. 실습 과제
1. PR마다 린트+테스트 실행, 실패하면 머지 불가(브랜치 보호 규칙).
2. main 머지 시 Docker 이미지 빌드 → ECR 푸시(OIDC 사용, 장기 키 없음).
3. 이미지 태그를 커밋 SHA로, 배포 후 헬스체크 실패 시 자동 롤백.
4. dev→staging→prod 환경 분리, prod는 수동 승인.
5. 같은 파이프라인을 Jenkinsfile로 재현해 Actions와 비교표 작성.
6. Trivy/gitleaks를 파이프라인에 추가(HIGH 취약점 시 실패).
7. kind에 ArgoCD 설치 → Git 저장소의 Helm 차트를 동기화, 클러스터에서 수동 변경하면 self-heal로 복구되는 것 확인.
8. 앱 저장소 CI가 매니페스트 저장소의 이미지 태그를 자동 갱신(PR 생성).
9. (심화) Argo Rollouts로 카나리 배포 + 메트릭 기반 자동 중단.
10. (심화) 파이프라인 시간 측정 → 캐시/병렬화로 50% 단축 수치화.
