# 06-1. 이력서·포트폴리오 작성법 (직무 전환자 기준)

## 1. 큰 전략
- 직무 전환자의 약점: "인프라 실무 경력 없음". 강점: **전 직무의 도메인 경험 + 자기주도 학습 + 운영 가능한 프로젝트**.
- 서류에서 보여줄 3가지: ① 이 분야에서 **실제로 구축·운영해 본 증거**(프로젝트, 수치) ② **기본기**(Linux/네트워크/클라우드 자격증과 설명 능력) ③ **전직 경험이 연결되는 지점**(예: 이전 직무의 고객 대응/데이터/개발/운영 경험).
- 채용 담당자는 서류 한 장당 30초~1분. **상단 3분의 1**에 핵심을 배치.

## 2. 이력서 구조 (1~2페이지)
1. **헤더**: 이름, 이메일, 전화, GitHub, 블로그, LinkedIn.
2. **한 줄 요약(Summary, 3~4줄)**: 지원 직무에 맞춘 정체성.
   - 예: "5년간 [이전 직무]에서 [성과]를 만들다, 서비스 안정성과 자동화에 매력을 느껴 클라우드/DevOps로 전환했습니다. AWS 3-tier 인프라를 Terraform으로 코드화하고 GitHub Actions로 배포를 자동화한 프로젝트 5개를 운영했으며, AWS SAA를 취득했습니다."
3. **기술 스택**: 숙련도 구분(상/중/하 대신 "사용 경험 있음/프로젝트에서 실무 사용"). 모르는 것을 나열하지 말 것.
   - Cloud: AWS(EC2, VPC, ALB, RDS, S3, IAM, EKS) / IaC: Terraform, Ansible / Container: Docker, Kubernetes, Helm, ArgoCD / CI/CD: GitHub Actions, Jenkins / Monitoring: Prometheus, Grafana, Loki / OS: Ubuntu, Rocky / Lang: Python, Bash
4. **프로젝트** (가장 중요, 아래 형식)
5. **경력**: 전 직무를 인프라 관점으로 재해석해 기술(성과 수치 포함).
6. **자격증/교육**: 최신순. 부트캠프/교육 과정은 프로젝트 성과 중심.
7. **학력**.
- 피할 것: 사진·가족사항 과다, 자기소개서식의 추상적 문장("열정적인", "성실한"), 사용해 보지 않은 기술 나열, 오탈자, 개인 정보 과다.

## 3. 프로젝트 기술 형식: STAR + 수치
```
[프로젝트명] AWS 3-tier 인프라 Terraform 코드화 (개인, 2주) | GitHub: ...
- 배경/문제: 콘솔 수작업으로 구성하면 재현이 어렵고 환경 간 차이가 발생
- 내가 한 일: VPC(2AZ), ALB, ASG, RDS를 Terraform 모듈로 작성, S3+DynamoDB 원격 state, PR 시 plan 자동 코멘트(GitHub Actions)
- 결과: 환경 구축 시간 2시간 → 12분, 동일 코드로 dev/prod 2개 환경 재현, Checkov 보안 이슈 14건 → 0건
- 트러블슈팅: NAT Gateway 비용 이슈를 VPC Endpoint 적용으로 월 예상 비용 $38 → $14로 절감
- 기술: Terraform, AWS(VPC, ALB, ASG, RDS), GitHub Actions, Checkov
```
- 동사로 시작: 구축, 자동화, 단축, 절감, 분석.
- **"무엇을 썼다"가 아니라 "무엇을 해결했다"**.
- 수치를 만들 수 없으면 만들 수 있게 실험(전/후 측정)하세요.

## 4. 직무 전환자용 경력 재해석 예시
- **개발자 출신**: "배포 자동화 직접 구축(수동 1시간 → 자동 10분), 장애 시 로그 분석 경험" → DevOps/SRE 어필.
- **서버/시스템 관리·SI 출신**: "서버 200대 관리 경험 + Ansible로 패치 자동화(작업 시간 70% 감소)" → 클라우드 전환 어필.
- **비 IT/CS 출신**: "고객 장애 대응/운영 프로세스 개선 경험, 문서화/커뮤니케이션 강점" + 프로젝트 비중 확대.
- **데이터/분석 출신**: "데이터 파이프라인·SQL·모니터링 경험" → MLOps/데이터 플랫폼 어필.
- **QA/테스트 출신**: "테스트 자동화/CI 경험" → DevOps 어필.

## 5. 포트폴리오 (GitHub + 노션/블로그)
- **GitHub**: 프로필 README에 핵심 프로젝트 6개 이내를 한눈에. 각 저장소는 [04번](04-포트폴리오-프로젝트.md)의 README 템플릿. 커밋 이력을 정직하게(한 번에 몰아 올리지 말고 작업하며 커밋). 불필요/반쯤 완성된 저장소는 private 처리.
- **아키텍처 다이어그램**: 이미지 상단에. 읽는 사람이 코드를 열지 않아도 이해 가능해야 함.
- **블로그**: "문제 → 원인 → 해결" 트러블슈팅 글 10편이면 매우 강력한 신호(예: "EKS Pod가 Pending인 7가지 이유"). 학습 정리글보다 **삽질 기록**이 신뢰를 줌.
- **데모**: 가능하면 짧은 영상/GIF(배포·롤백 시연).
- **비용 주의**: 라이브 URL을 유지하기 어렵다면 영상으로 대체.
- 면접 대비: 프로젝트마다 "왜 이 기술을 선택? 대안은? 장애 시나리오는? 보안은? 비용은? 확장하려면?" 6가지 질문에 답할 수 있어야 함.

## 6. 자기소개서/지원 동기 문장 (핵심)
- 회사별로 첫 문단을 바꾸세요: 회사 기술 블로그/채용 공고를 읽고 "어떤 문제를 풀고 있는지"를 한 줄로 언급.
- 예: "귀사 기술 블로그의 '쿠버네티스 노드 비용 40% 절감' 글을 읽고, 저도 개인 프로젝트에서 Karpenter와 Spot 인스턴스로 비슷한 문제를 실험해 보았습니다."

## 7. 이력서 자가 점검 체크리스트
- [ ] 첫 화면 30초에 "이 사람은 클라우드/DevOps를 할 수 있다"가 보이는가
- [ ] 프로젝트 3개 이상에 수치가 있는가
- [ ] 링크(GitHub/블로그)가 열리고 README가 정돈되어 있는가
- [ ] 공고의 필수 키워드가 이력서에 자연스럽게 있는가(ATS/키워드 검색 대비)
- [ ] 거짓/과장이 없고, 모든 문장을 면접에서 5분 설명할 수 있는가
- [ ] 전직 경험이 새 직무와 연결되어 설명되는가
- [ ] 오탈자·날짜·연락처 오류가 없는가(지인 2명에게 리뷰 요청)

## 8. 지원 운영
- 지원 현황표(회사/직무/링크/지원일/상태/배운 점). 주 10곳 이상 지원, 서류 통과율 10~15%가 일반적이라 가정.
- 공고마다 이력서를 **키워드/프로젝트 순서 조정**(핵심 프로젝트를 위에).
- 채용 경로 병행: 원티드/사람인/점핏/로켓펀치 + 링크드인 + 커뮤니티 + 지인 추천 + 기술 컨퍼런스 네트워킹 + 오픈 채용 설명회.
- 불합격 사유를 면접 후 즉시 복기해 06-3 질문 답변을 수정.
